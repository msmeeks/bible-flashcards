## Duplicated verse-reference-resolution logic in AddVerseScreen causes inconsistent "unresolved book" UX

**Severity:** Major (correctness / code quality)

The fix for "resolve custom book-name variants before Add Verse web lookup" copy-pasted the entire normalize/fetch-custom-variants/handle-failure block from `_normalizeAndAwaitConfirmation()` (`lib/screens/verses/add_verse_screen.dart:280-309`) into `_lookupVerse()` (`lib/screens/verses/add_verse_screen.dart:183-206`) instead of extracting a shared helper. The two copies have already drifted: `_normalizeAndAwaitConfirmation()` sets `_referenceUnresolved = true` on an unresolved-book failure, which reveals the "Open Book Name Variants settings" shortcut button. The copy in `_lookupVerse()` only sets `_lookupError` and never sets `_referenceUnresolved`, so a user who hits an unrecognized book name via the **Search** button never sees the shortcut link that the equivalent **Save** path shows — even though the error text tells them to "Add a custom variant in Book Name Variants settings." The user-facing error string itself is also duplicated verbatim (plus a third, truncated variant), so the copy can drift out of sync in three places. This gap has no test coverage — the only unresolved-book test targets the save path (`test/screens/verses/add_verse_screen_test.dart:433`).

**Suggested fix:** extract a single `Future<Map<String,String>> _loadCustomVariants()` / `_resolveReference(String raw)` helper used by both call sites, hoist the error string to a shared constant, and make both failure paths set `_referenceUnresolved` consistently.

## Hardcoded tab count in MainScaffold can silently drift from the destinations list

**Severity:** Minor (style / maintainability)

`lib/screens/main_scaffold.dart:27` hardcodes `List.generate(5, (_) => GlobalKey<NavigatorState>())` to match the 5 entries in `_destinations`, and `build()` makes 5 separate `_tabNavigator(...)` calls. If a tab is ever added or removed, these counts can drift out of sync with no compiler error.

**Suggested fix:** use `List.generate(_destinations.length, (_) => GlobalKey<NavigatorState>())`.

## Back button exits the app immediately from any non-Home tab with no local nested history

**Severity:** Minor (UX / product decision)

`PopScope.onPopInvokedWithResult` (`lib/screens/main_scaffold.dart:74-84`) only checks the *current* tab's nested Navigator; if that tab has no pushed sub-screens, it calls `SystemNavigator.pop()` directly, closing the app from e.g. the Test or Settings tab without first returning to Home. This matches legacy single-root-route behavior, so it's not a regression, but it diverges from the common Android pattern of routing back-from-non-Home-tab to Home before exiting.

**Suggested fix:** product decision — if desired, route back-press at a tab root to the Home tab instead of exiting, exiting only from Home.

## IndexedStack keeps inactive tabs' controls in the semantics/focus tree

**Severity:** Major (accessibility — WCAG 2.4.3 Focus Order, 1.3.2 Meaningful Sequence, 4.1.2 Name/Role/Value)

Each of the 5 tabs now hosts its own nested `Navigator` with its own push history (e.g. a half-filled Add Verse form, an open Verse Detail screen), all kept alive simultaneously inside a single `IndexedStack` (`lib/screens/main_scaffold.dart:85-98`). `IndexedStack` only hides non-selected children *visually* — it does not remove them from the semantics tree or keyboard focus-traversal order. Now that tabs retain arbitrarily deep push stacks, a TalkBack user doing linear swipe navigation, or a hardware-keyboard user tabbing through the screen, can land on controls belonging to a tab that isn't currently displayed.

**Suggested fix:** wrap each non-selected tab's Navigator in `ExcludeSemantics`:
```dart
children: List.generate(5, (i) => ExcludeSemantics(
  excluding: i != _selectedIndex,
  child: _tabNavigator(i, roots[i]),
)),
```

## Disabling in-flight action buttons drops keyboard/TalkBack focus with no restore

**Severity:** Major (accessibility — WCAG 2.4.3 Focus Order)

Both the Add-variant dialog fix (`lib/screens/settings/book_variants_screen.dart:87-93,111-127`) and the new `_MemorizeButton` state (`lib/screens/verses/verses_screen.dart`) disable their primary button (`onPressed: null`) while an async operation is in flight. Since the project runs with a hardware keyboard enabled as a first-class input, this matters: when a focused button's `onPressed` becomes `null`, Flutter clears `FocusManager.primaryFocus` and doesn't move it anywhere, so a keyboard user's next Tab press restarts traversal from the top of the dialog/screen, and a TalkBack user's focus indicator disappears mid-interaction.

**Suggested fix:** capture the focused node before disabling the button and re-request it once `isSubmitting`/`_isMemorizing` clears, rather than relying solely on the `Semantics(liveRegion: true, ...)` spinner label to communicate state.

## Back gesture during in-flight submission gives no accessible feedback

**Severity:** Minor (accessibility — WCAG 4.1.3 Status Messages, nice-to-have)

`PopScope(canPop: !isSubmitting, ...)` (`lib/screens/settings/book_variants_screen.dart:41-42`) correctly prevents dismissing the dialog mid-save and does not create a permanent keyboard trap (canPop reverts to true once submission ends). However, a screen-reader or switch-access user who presses back while `isSubmitting` is true gets no feedback that their input was ignored beyond the visible spinner.

**Suggested fix:** consider a `SemanticsService.announce('Please wait…')` cue when a blocked pop is attempted.
