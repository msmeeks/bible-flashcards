## Deduplicate verse-lookup-by-ID logic between test result and history screens

**Severity:** Major · **Category:** code (DRY)

`lib/screens/test/test_result_screen.dart:35-45` and `lib/screens/settings/test_history_screen.dart:58-69` both independently implement the identical pattern: collect unique `verseId`s from results, `Future.wait` over `db.getVerseById(id)` calls, build a `Map<String, Verse?>`, and render `verse?.reference ?? '$id (verse deleted)'` with italic fallback styling.

This is a DRY violation — the same "resolve verses referenced by test results, tolerate deleted verses" concern is implemented twice.

**Suggested fix:** extract a shared helper (e.g. `Future<Map<String, Verse?>> loadVersesByResult(List<VerseTestResult>, DatabaseHelper)` or a small `VerseResultLookup` service) used by both screens, and share the deleted-verse rendering logic too if feasible.

## Batch verse lookups instead of N+1 individual DB queries

**Severity:** Major · **Category:** code (efficiency)

`lib/screens/test/test_result_screen.dart:38-43` and `lib/screens/settings/test_history_screen.dart:61-67` call `getVerseById` once per unique verse ID via `Future.wait`, rather than a single batched `WHERE id IN (...)` query. For history screens with unbounded result history, this generates one DB round trip per distinct verse.

**Suggested fix:** add a `DatabaseHelper.getVersesByIds(Set<String>)` batch method and use it in both places — this also resolves the DRY finding above by centralizing the logic.

## Legacy settings migration has no error handling and can block app startup

**Severity:** Major · **Category:** code + test coverage (correctness/reliability)

`lib/main.dart:13` calls `await LegacySettingsMigration.clearStaleDriveSignInFlag();` unconditionally at startup with no try/catch. `_secureStorage.delete()` on a non-existent key is normally a no-op, but if `flutter_secure_storage`/Android Keystore throws (e.g. Keystore corruption after an OS update — a real-world failure mode for this plugin), the entire app fails to launch before the database or settings even load.

`test/services/legacy_settings_migration_test.dart` only covers the success case (mocked channel returns `null`); there is no test for a thrown `PlatformException`.

**Suggested fix:** wrap the call in `main.dart` in try/catch (swallow-and-log, since this is best-effort cleanup), and add a test asserting the migration doesn't propagate an exception from the platform channel.

## Add-verse save-confirmation dialog restores focus to the wrong control

**Severity:** Major · **Category:** accessibility (WCAG 2.4.3 / 2.4.11)

`lib/screens/verses/add_verse_screen.dart:334-336` — `_saveVerse()` invokes the Save confirmation dialog, but on close always calls `_searchFocusNode.requestFocus()` (the Search button, not Save). This focus-restore pattern was copied from `_ensureConsentFor` (line 160-161), where it's correct because Search invoked it there — but it's wrong when reused for the Save flow.

Screen-reader/keyboard users lose their place: focus jumps to an unrelated control after the dialog closes.

**Suggested fix:** track a `_saveFocusNode` (or otherwise pass in whichever control opened the dialog) and restore focus to that control specifically.

## Google Sign-In OAuth grant left unrevoked after Google Drive backup removal

**Severity:** Minor (blast radius limited to `drive.appdata` scope) · **Category:** security / privacy

`lib/services/google_drive_service.dart` (deleted) previously called `GoogleSignIn.instance.disconnect()` on explicit sign-out, fully revoking the OAuth grant. For users who had previously connected Drive backup and upgrade straight to this build, that code path is now unreachable — `google_sign_in`'s own persisted authentication state (Android account/credential manager, outside this app's `flutter_secure_storage`) is left untouched, and the `google_sign_in`/`googleapis` packages are removed from `pubspec.yaml` entirely, so there's no code left in the app to call `disconnect()`.

The residual grant only allows `drive.appdata` scope (low blast radius), but it's still a silent, unrevoked credential the user isn't told about — relevant to the GDPR data-minimization expectations in `meta/PRIVACY.md`.

**Suggested fix:** add a one-time best-effort `GoogleSignIn.instance.disconnect()` call inside `LegacySettingsMigration` before the package removal ships, or document in release notes that users should manually revoke Drive access.

## Orphaned unencrypted SharedPreferences keys from removed Drive backup settings not cleared

**Severity:** Minor · **Category:** privacy (data minimization/retention)

`LegacySettingsMigration` only deletes the `drive_signed_in` flag from `flutter_secure_storage`. The now-removed `drive_backup_enabled`, `backup_cadence`, `last_backup_at`, `drive_consent_at`, `drive_consent_version` keys previously written to plaintext `SharedPreferences` are never deleted for existing users — they simply become unread. **Suggested fix:** add cleanup of these `SharedPreferences` keys to `LegacySettingsMigration` alongside the secure-storage flag.

## Mic "stop" safety-net reuses the full 15s listening timeout, appears unresponsive after manual stop

**Severity:** Minor · **Category:** code (UX/correctness)

`lib/screens/test/test_session_screen.dart:192-209, 280-283` — when the user taps to stop listening, `_startMicTimeout(verseIndex)` is restarted with the same `_micTimeoutDuration = Duration(seconds: 15)` used for detecting a wedged *start*. If the plugin fails to fire `onStopped`/`onTranscript` after `stopListening()` resolves, the UI can appear stuck on "Listening…" for up to 15 seconds after the user explicitly tapped stop.

**Suggested fix:** use a shorter, dedicated timeout (e.g. 3-5s) for the post-stop safety net, distinct from the initial-start wedge timeout.

## Redundant concurrent reference resolution between blur handler and Save in add-verse screen

**Severity:** Minor · **Category:** code (efficiency/fragility)

`lib/screens/verses/add_verse_screen.dart:78-110` (`_normalizeReferenceOnBlur`) and `:291-322` (`_saveVerse`) — tapping Save removes focus from the reference field, firing an async DB-backed resolution via blur, while `_saveVerse` performs its own independent resolution concurrently. Both hit the DB and mutate state independently. Not currently observed to cause incorrect saves, but it's wasted work and fragile if the two resolution paths diverge in future edits.

**Suggested fix:** have `_saveVerse` await/reuse the blur-triggered resolution instead of re-running it independently.
